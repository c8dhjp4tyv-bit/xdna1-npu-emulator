## Stage 3 observation

Normal mode used `intel_iommu=on,sm_on iommu=on` with QEMU
`intel-iommu,svm=on,pasid-bits=20,scalable-mode=on,fsts=on`. The stock driver
completed its translated SVA/PASID probe/context path; QEMU's MERT trace records
`context ... pasid 1` as context metadata. QEMU publishes the endpoint ATS/PASID/PRI capabilities
for this probe/context compatibility path, but QEMU 11.1.1 does not provide a
context-aware PASID DMA accessor and `MemTxAttrs.pid` is only eight bits. The
emulator therefore does not claim PASID-tagged execution DMA; unsupported
execution opcodes still fail explicitly. The integration patch advertises
coherent Intel SVM (`SMPWC`) only when
SVM is explicitly enabled. PSP firmware validation uses the physical DMA
callback because the driver supplies a `virt_to_phys()` buffer; regular device
DMA remains on the PCI DMA/IOMMU callback without PASID tagging.

The force-IOVA run used the same translated vIOMMU plus
`amdxdna.force_iova=1`. The stock driver reported its private IOVA mode and
passed the same XRT checks. This is a supported compatibility path, not a
guest-driver modification. Stage 5 (BO/ DMA/array memory modeling) remains
**not started**; unsupported execution operations still fail explicitly.

Suspend/resume was not requested for this disposable boot.
